# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 某樣菜的客人沒進門（被討厭的菜擋住），或那天根本沒有想吃它的客人 | 先查是誰想吃這樣菜、那天有沒有來、有沒有被擋在門外；那天沒人會買就不上架，有人買就照「明天建議備貨」調整份數；合計報廢盡量壓在 15 份以下，避免多付 50 元清運費 |
| 嫌太貴很多 | 價格超過客人剩下的預算 | 前兩天把那樣菜降價（照 `pricing-rules` 心法 1）；第 5 天可以不理會 |
| 想吃的沒上架很多 | 那天有一群客人想吃的菜沒上架（例如第 2 天外送員只喝酸辣湯） | 查客人表，看那天來的是誰、想吃什麼，把人數多的那樣菜排進當天的 4 樣菜單；名額不夠時，拿掉賣得最少、或會擋客人進門的那一樣 |
| 因為討厭的菜不進門 | 上架了某群客人討厭的菜，他們整群不進門，連帶他們想吃的菜也賣不掉 | 比較兩邊客人的人數和預算，看留下哪一群比較賺。官方客人包裡，不上架韭菜鍋貼、改上酸辣湯，資金從 3,806 提高到 5,911 |
| 星等往下掉 | 不滿的客人太多：不滿 ≥ 25% 掉半顆，≥ 40% 掉一顆。不滿包含沒上架、賣完、太貴 | 看那天「沒買到」的原因中哪一項最多，就先處理那一項 |
| 我自己發現的現象：飲料報廢很多 | 鍋貼太貴，預算被吃光，客人買不起飲料 | 鍋貼定高價的日子，飲料少備（照 `pricing-rules` 心法 3） |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
